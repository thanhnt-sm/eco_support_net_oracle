# DG019: dialect and source locations

DG019 checks raw SQL with the configured provider's grammar. Currently only `sqlserver` has a grammar parser (ScriptDOM T-SQL). Oracle, PostgreSQL and MySQL raw SQL grammar checks are **unevaluated**, not successful validation. Acquisition errors still produce DG019. Unevaluated contracts normally make the CLI return exit code 3; `--allow-unevaluated` permits an incomplete run to finish according to its other findings, without turning missing validation into a pass. This applies in both IDE-safe and trusted runs; no database access is added.

Provider precedence is `--provider`, then `.dataguard.yml` `DefaultProvider`, then `sqlserver`. Custom `DataContext.ExecuteNonQuery(sql)` wrappers are detected by method name and the first SQL-shaped argument. They usually provide no connection-provider hint. DataGuard does not infer Oracle merely because an alias resembles Oracle syntax. Confirm the configured provider before changing SQL. For a confirmed Oracle application, configure `DefaultProvider: oracle`; this prevents T-SQL grammar checks but does not supply Oracle grammar validation. Existing dialect and schema rules still apply.

Oracle supports target aliases in [UPDATE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/UPDATE.html) and [DELETE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/DELETE.html). For example, `UPDATE SAMPLE_RECORD rec SET rec.AMOUNT = :amount WHERE rec.ID = :id` and `DELETE FROM SAMPLE_CONTACT contact WHERE contact.ORGANIZATION_ID = :id` use Oracle forms. SQL Server uses different alias forms, such as `UPDATE rec SET AMOUNT = @amount FROM SAMPLE_RECORD rec WHERE rec.ID = @id`. Do not rewrite production SQL without understanding its actual provider and semantics.

The DG019 message names the grammar and labels its line/column as **SQL-relative** (one-based, in the extracted SQL, including leading newlines). Interpolation/concatenation values become placeholders, so these columns are not C# columns. Placeholder normalization inside ScriptDOM is mapped back to that extracted input. Visual Studio's separate Line/Column columns and double-click navigation use C# source coordinates from SARIF. They are not the coordinates embedded in the message.

For invocation arguments, command-text assignments and standalone constants, extracted SQL retains source provenance. Errors within unchanged literal text navigate to the original C# character, including after interpolation/concatenation and with LF or CRLF. Generated values and escaped/raw literal text without an exact map point to the containing expression/token. End-of-input errors, unresolved provenance, and acquisition sources without a map retain the original acquisition location (often the SQL call). The map is accepted only if its reconstructed text equals the actual extracted SQL. This does not improve the existing extractor's data-flow analysis of later assignments or arbitrary wrapper bodies.

DG019 is emitted by the validation pipeline to SARIF. It is not a new Roslyn IDE analyzer diagnostic; the standalone analyzer has a separate diagnostic inventory. SARIF stores one-based C# coordinates; the VS presenter converts them once to zero-based ErrorTask/buffer coordinates (PR59). An Error List screenshot without the editor/caret cannot establish navigation correctness. Verify double-click navigation manually in the installed VS version.

Oracle grammar expansion needs a separately evaluated parser/grammar and dialect conformance corpus. A regex alias exception or transformation into T-SQL would not establish validity. Offline grammar support and explicitly authorized live validation have different safety requirements; this change adds neither Oracle parsing nor live execution.
