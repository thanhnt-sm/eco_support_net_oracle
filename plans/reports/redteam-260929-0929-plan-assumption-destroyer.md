## Finding 1: VS Code `--ide-safe` silently disables the SecretStorage connection-string workflow for `validate`, and the CLI's suppression notice is filtered out of the Output channel
- **Severity:** High
- **Location:** `plan.md` "Added during execution" (VS Code also passes `--ide-safe`); Phase 01 Requirements (`DATAGUARD_CONNECTION_STRING` ignored). Implementation gap not covered by any phase: no VS Code phase exists.
- **Flaw:** VS Code injects the user's *own* consented credential via `DATAGUARD_CONNECTION_STRING` (`src/DataGuard.VSCode/src/extension.ts:509-511`) and, in the same spawn, passes `--ide-safe` for `validate` (`command-args.ts:43-44`). The CLI resolves env → `ConnectionString` (`CliConfigurationResolver.cs:21-25`) and then `IdeSafePolicy.Apply` strips it (`IdeSafePolicy.cs:43-49`, called at `Program.cs:237-247`). The only notice is the stderr line `ide-safe: suppressed connection string from DATAGUARD_CONNECTION_STRING/config …`, which `processProgressText` drops (`extension.ts:644-661` echoes only `{Kind:…}` JSON or lines starting with `[INFO]/[WARN]/[ERROR]`), and the exit≠0 `rawErrors` filter (`extension.ts:471-476`) needs `Error|fail|Exception` — not present. The policy treats a user-supplied secret as if it were repo-controlled; the threat model in `command-args.ts:5-10` is about `.dataguard.yml`, not SecretStorage.
- **Failure scenario:** Developer runs "Configure Connection Credential", then "Run Validation" in a trusted workspace. CLI runs snapshot-or-source-only, exits 0, "0 findings", status idle. No DB rule ran; nothing tells them. `README.md:31,45` of the VS Code extension still advertises the credential as "passed only to the spawned CLI process".
- **Evidence:** `extension.ts:509-511`, `command-args.ts:43-44`, `Program.cs:237-247`, `IdeSafePolicy.cs:43-49`, `extension.ts:644-661`, `extension.ts:471-476`, `src/DataGuard.VSCode/README.md:31,45`.
- **Suggested fix:** Either (a) do not pass `--ide-safe` when a SecretStorage credential is present *and* `workspace.isTrusted` (the credential is user consent, not repo input), or (b) add a CLI carve-out (`--ide-safe` keeps env connection, still strips config/`ManualAssemblyPath`/secret managers) — pick (b) if the goal is "never let repo config pick the DB"; and in all cases echo stderr lines starting with `ide-safe:` as `[WARN]` in the channel. Update the VS Code README.
- **Test that would catch it:** Unit test feeding `"ide-safe: suppressed connection string …\n"` through `processProgressText` and asserting a channel line is appended (fails today: nothing appended).

## Finding 2: VS Code has no old-CLI detection; every currently released CLI rejects `--ide-safe` with exit 1, which the extension reports as "found findings"
- **Severity:** High
- **Location:** `plan.md` "Added during execution"; Phase 02 Req 2 defines old-CLI handling for VS only. Implementation gap: no VS Code equivalent.
- **Flaw:** VS Code does not bundle the CLI (package only bundles the LSP server, `scripts/package-lsp.cjs:8-11`); default `cliPath` is the global tool `dataguard` (`extension.ts:395`). `--ide-safe` first appears in unreleased commit df442b9; the newest tag is v0.2.2. A System.CommandLine parse error exits **1** and prints `Unrecognized command or argument '--ide-safe'.` to stderr. VS Code maps `exitCode === 1` to a warning toast "DataGuard validate found findings" (`extension.ts:561-563`), the stderr line matches neither the `rawErrors` filter (`:475`) nor `processProgressText` (`:659`), and `loadDiagnostics` prints "SARIF output was unavailable or exceeded size limit (50MB)" (`:733-735`). VS, by contrast, detects and stops (`CliArgumentBuilder.cs:103-114`, `ProgressStreamReader.cs:66-69`, `DataGuardPackage.Commands.cs:148-154`).
- **Failure scenario:** Marketplace auto-updates the extension to 0.2.3; the user's global CLI stays 0.2.2 (`dotnet tool update` is manual). Every Validate/Assess: exit 1 → "found findings" toast, "SARIF unavailable", zero diagnostics, no actionable message. Support load, and the security posture ("VS Code passes `--ide-safe`") is only true for users who also upgraded the CLI.
- **Evidence:** `extension.ts:395,430,471-476,561-563,644-661,733-735`; `command-args.ts:44,47`; `git tag` (v0.2.2 latest); `git log -S'System.CommandLine'` (beta4 → 2.0.12 only in this branch); S.CL 2.0.12 resource string (see contract table).
- **Suggested fix:** Port `IsIdeSafeUnsupportedMessage` to `extension.ts` (check stderr buffer after exit), show an error with `dotnet tool update -g DataGuard.Cli`, never fall back; or add a `dataguard --version` preflight with a minimum version constant shared with `package.json`.
- **Test that would catch it:** `waitForExit` with a fake child that writes `Unrecognized command or argument '--ide-safe'.` to stderr and exits 1 → expect error status + update hint (today: warning "found findings").

## Finding 3: The plan's VS↔CLI rejection contract is wrong (exit 2 vs 1), the detector is a negative string match on a third-party library's wording, and the only test encodes an impossible stream
- **Severity:** Medium
- **Location:** Phase 02 Requirements #2 ("If the CLI exits 2 and stderr mentions `--ide-safe`"); Phase 01 Security section says exit 1. The two phases contradict each other.
- **Flaw:** System.CommandLine returns 1 on parse errors; the implementation works only because it ignores the exit code entirely (`DataGuardPackage.Commands.cs:148` checks `outcome.Progress.IdeSafeUnsupported` alone). Safety therefore rests on `CliArgumentBuilder.cs:109-114` matching two hard-coded English phrases from a library the CLI does not control (beta4 wording is unverified — package not cached; a future S.CL wording change, a wrapper exe, or any CLI that swallows the parse error and exits 0 defeats it). There is no *positive* handshake proving ide-safe was honoured. `CliArgumentBuilderTests.cs:43-62` asserts a stream containing both the rejection line and a `Summary` event — no real CLI produces both, so the test does not exercise the discard path end-to-end (`Commands.cs:148-154` has no test).
- **Failure scenario:** Custom CLI path points at a wrapper/fork that prints `error: option --ide-safe not supported` and exits 0 after running unsafely; VS publishes the results as ide-safe. Or S.CL 3.x rewords the error; VS 0.2.x silently accepts a non-ide-safe run.
- **Evidence:** `Program.cs:176-185` (option exists, no acknowledgement emitted), `IdeSafePolicy.cs:136-141` (suppression line only when something was suppressed), `Commands.cs:148-154`, `CliArgumentBuilder.cs:103-114`, `CliArgumentBuilderTests.cs:43-62`, phase-01 vs phase-02 text.
- **Suggested fix:** Make the CLI emit an unconditional stderr acknowledgement when `--ide-safe` is active (e.g. progress event `{"Kind":"PhaseStarted","Phase":"ide-safe"}` or line `ide-safe: active`) and have VS/VS Code **require** it before publishing; keep the negative match as a nicer error message. Fix phase-02 text to "exit 1".
- **Test that would catch it:** Fake CLI exits 0 with stderr `warning: --ide-safe ignored` and writes a SARIF → VS must discard (today: publishes).

## Finding 4: Consent is bound to a directory path, not to the solution/repository; build-triggered runs then auto-execute against whatever later occupies that path
- **Severity:** Medium
- **Location:** Phase 02 Requirements #1 and Security ("Consent hash invalidates when repo changes `.dataguard.yml`").
- **Flaw:** Key = SHA-256(upper-cased solution dir + `|` + config hash or `"absent"`) (`SolutionTrustGate.cs:61-68`). Nothing about the solution (`.sln` path/name/content) or repository identity enters the key. Two unrelated repositories cloned to the same folder with no `.dataguard.yml` (the common case for a fresh clone) share the key `"absent"`. The prompt promises "remembered for this solution until its `.dataguard.yml` changes" (`SolutionTrustGate.cs:84`) — it is actually remembered for the *folder*. Combined with `RunValidationOnBuild`, the first Build in the new repo runs the CLI with no question asked (`DataGuardPackage.Commands.cs:180-183` short-circuits before the `fromBuild` check).
- **Failure scenario:** Dev consents `C:\src\app` (their project, no config). Later `rm -rf C:\src\app; git clone <untrusted> C:\src\app`, opens the `.sln`, presses F6 → CLI immediately walks and Roslyn-parses the untrusted tree. Blast radius is bounded by `--ide-safe` (parse-only, 300 s timeout) — hence Medium, not High — but the trust question the plan introduced was never asked for this source, and a Roslyn parse of adversarial input is CPU/memory-unbounded inside the timeout.
- **Evidence:** `SolutionTrustGate.cs:61-68,84`, `DataGuardPackage.Commands.cs:57,180-190`, `SolutionTrustGateTests.cs:157-166` (asserts same key for same dir; no test for different solutions in the same dir).
- **Suggested fix:** Include the `.sln` full path (from `GetSolutionInfo`'s second out param, currently discarded at `Commands.cs:57`) and a hash of the `.sln` file in the key; optionally also `.git/HEAD`'s remote URL. Reword the prompt to match.
- **Test that would catch it:** `ComputeConsentKey(dir, slnA, null) != ComputeConsentKey(dir, slnB, null)` — fails today (API has no solution-file parameter).

## Finding 6: `ExitCodeExplainer` and the run log treat CLI exit 1 with a Summary as "found errors", but `validate` also exits 1 on an unhandled exception *after* a Summary was emitted, and exit 3 discards the SARIF that VS just cleared the Error List for
- **Severity:** Medium
- **Location:** Phase 02 Requirements #10 (exit-code explainer) and the "Clear policy" added by prior review (`Commands.cs:94-98`).
- **Flaw:** (a) `Program.cs:386-394` sets exit 3 and `return`s *before* the SARIF emitter runs (`:428-434`), so any repo whose `.dataguard.yml` sets `DefaultProvider: oracle|postgresql` (ProviderRuleCatalog `Unavailable` registrations; plan "Deferred") yields: Error List cleared at run start → no SARIF → "Validation produced no SARIF diagnostics" + "[WARN] Validation incomplete". The user loses the previous run's diagnostics on every build with nothing to replace them — the clear-at-start policy assumed a SARIF would follow. (b) `Explain("validate", 1, hasSummary:true)` → "found errors" (`ExitCodeExplainer.cs:24-27`), but `Program.cs:495-500` also produces exit 1 + Summary when an exception is thrown after the Summary event (SARIF write failure at `:428-434` is inside the same `try`). VS then says "found errors. See Error List" while the Error List is empty.
- **Failure scenario:** SARIF `--output` path in `%TEMP%` becomes unwritable (AV lock, disk full) → CLI prints `Validation failed: …` and exits 1 after Summary → VS: "Validation found errors. See Error List." with 0 items, status bar "N errors, M warnings".
- **Evidence:** `Program.cs:380-394,428-434,495-500`; `ExitCodeExplainer.cs:24-27`; `DataGuardPackage.Publishing.cs:17-21,62-65`; `Commands.cs:94-98`.
- **Suggested fix:** In VS, when `hasSummary && exit==1 && diagnosticCount==0 && !File.Exists(sarif)` explain as "CLI failed after summary — see [DataGuard CLI] lines". Move the Error List clear to just before `Publish` (keep old items on exit 3 / no-SARIF) or keep the clear but write an explicit "previous results cleared; no new results" line.
- **Test that would catch it:** `ExitCodeExplainer`/publisher test: exit 1, Summary present, SARIF missing → message must not say "See Error List" (fails today).

## Finding 7: SECURITY.md and the plan generalise "VS Code runs the CLI with `--ide-safe`", but two of the four workspace-driven VS Code commands don't, and `verify-shape` sends repo-extracted SQL to the developer's live database with no consent step
- **Severity:** Medium
- **Location:** Phase 04 (SECURITY.md wording); `plan.md` "Added during execution … so the security docs' claim holds for both hosts".
- **Flaw:** `SECURITY.md:41-44`: "the Visual Studio and VS Code extensions run the CLI with `--ide-safe`". `command-args.ts:52-74` builds `scan` and `verify-shape` without `IDE_SAFE_FLAG`; both are exposed as workspace commands (`extension.ts:113-115`) and, unlike `snapshot`/`baseline` (`extension.ts:317-325` modal), run with no confirmation. `verify-shape` takes the SecretStorage credential from env (`Program.cs:640-648`), extracts every `Read` SQL literal from the workspace's C# (`:686-690`) and ships each to the DB via `sp_describe_first_result_set` / `SELECT * FROM (…) WHERE 1=0` (`LiveSqlShapeValidationRule.cs:45`, `OracleLiveQuerySchemaProvider.cs:86-100`, `PostgreSqlLiveQuerySchemaProvider.cs:85-118`). The providers are describe-only with stacked-query rejection (`:39-45`), so this is not SQL execution — but a hostile repo chooses the text compiled by the developer's production DB (schema probing, planner DoS, error-message leakage into the channel). The plan's trust model ("bounds what a run can do even in a trusted workspace whose files were tampered with", `command-args.ts:5-10`) does not hold for this command, and the docs say it does.
- **Failure scenario:** Trusted workspace (VS Code trust granted for a fork), credential configured for a shared staging DB; user clicks "Verify Shape"; 500 attacker-authored `SELECT` literals are compiled against staging; errors (`ORA-…`, table names) land in the Output channel.
- **Evidence:** `SECURITY.md:41-44`; `command-args.ts:52-74`; `extension.ts:113-115,317-325`; `Program.cs:640-690`; `LiveSqlShapeValidationRule.cs:45`; `OracleLiveQuerySchemaProvider.cs:39-45,86,100`.
- **Suggested fix:** Either put `verify-shape` behind the same modal as `snapshot`/`baseline`, or scope the SECURITY.md/README sentence to `validate`/`assess` and list the live-DB commands explicitly. `scan` should pass `--ide-safe` too (harmless today, keeps the invariant honest).
- **Test that would catch it:** `command-args.test.ts` loop asserting `--ide-safe` for every command except `snapshot`/`baseline` (fails today for `scan`/`verify-shape`); docs-sync check that every command named in SECURITY.md's claim is in that set.

## Finding 8: `IdeSafePolicy` sanitises a value copy; anything that re-reads the environment or config file after the copy escapes it — today that is only `verbose` connection discovery, but the design has no guard and no test
- **Severity:** Medium
- **Location:** Phase 01 Architecture ("Program.cs calls it right after `ResolveCommandConfiguration`") and Success criteria ("`DATAGUARD_CONNECTION_STRING` never reaches an adapter").
- **Flaw:** The policy returns a new record (`IdeSafePolicy.cs:24-76`); the original `configPath`, the env var and `Environment` remain available to everything downstream. `CredentialManager.GetConnectionStringAsync` (`src/DataGuard.Core/Security/CredentialManager.cs:60-64`) and `ZeroTrustCredentialProvider` (`:114`) re-read `DATAGUARD_CONNECTION_STRING` directly — today they are reached only via `PublicApiSurface` (`PublicApiSurface.cs:77,557`), not the `validate` handler, so the success criterion holds *by accident of call graph*, not by construction. There is no test that runs `validate --ide-safe` end-to-end with the env var set and asserts no adapter is constructed; `IdeSafePolicyTests` (per phase-01 Todo) tests the pure function only, and the plan itself lists "end-to-end `--ide-safe` handler wiring" as a deferred test gap.
- **Failure scenario:** A future refactor routes `validate` through `PublicApiSurface`/`CredentialManager` for rotation detection (the class exists for exactly that) → env connection string is re-acquired after the policy stripped it → live DB connection under `--ide-safe`; no test fails.
- **Evidence:** `IdeSafePolicy.cs:24-76`; `Program.cs:237-247`; `CredentialManager.cs:60-64`; `ZeroTrustCredentialProvider.cs:114`; `PublicApiSurface.cs:77,557`; `plan.md` "Deferred from review … end-to-end `--ide-safe` handler wiring".
- **Suggested fix:** Make ide-safe a process-level fact: after `Apply`, `Environment.SetEnvironmentVariable("DATAGUARD_CONNECTION_STRING", null)` (and `VAULT_TOKEN`, `ConnectionStrings__*` read by `AutoDetectionEngine.cs:298-300`) inside the CLI process, and add a static `IdeSafePolicy.IsActive` that adapter constructors assert against. Add the end-to-end test now rather than deferring it.
- **Test that would catch it:** Integration test: set `DATAGUARD_CONNECTION_STRING=Server=127.0.0.1,1;…`, run `validate --ide-safe --project <fixture>`, assert no socket connect attempt (or inject a throwing adapter factory) — currently absent.
