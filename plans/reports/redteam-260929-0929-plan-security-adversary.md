## Finding 1: Extension text tells users to `dotnet tool install -g DataGuard.Cli` — that package ID is unclaimed on nuget.org
- **Severity:** High
- **Location:** Phase 02, section "Requirements" item 3 ("Remove `TryAutoInstallCliAsync`; replace with actionable message"); Phase 04 docs
- **Flaw:** The auto-install was replaced with guidance to install from the default NuGet feed, but `DataGuard.Cli` does not exist there. `https://api.nuget.org/v3-flatcontainer/dataguard.cli/index.json` → HTTP 404; `azuresearch-usnc.nuget.org/query?q=packageid:DataGuard.Cli&prerelease=true` → `totalHits: 0`. The ID is packable (`DataGuard.CrossPlatform.slnf:9` includes the Cli project, `release.yml:111` packs it, `:554` pushes only when a key is present) but has never been published or reserved, so anyone can squat it. `CliLocator.StandardInstallCandidates()` probes `%USERPROFILE%\.dotnet\tools\dataguard.exe` (`CliLocator.cs:106`) — exactly where `dotnet tool install -g` drops a squatted binary — and the message is emitted precisely when the bundled CLI is absent, i.e. when that probe will be the one that wins.
- **Failure scenario:** Attacker publishes `DataGuard.Cli` on nuget.org with a `dataguard` tool that mirrors the real CLI's stderr/SARIF contract. A user whose VSIX install lost `cli\dataguard.exe` (or who follows the "CLI too old" message from Finding 2) runs the suggested command; the squatted tool becomes the CLI used by Visual Studio, VS Code (`extension.ts:865` gives the same instruction) and the shell. `--ide-safe` is meaningless — the attacker owns the process.
- **Evidence:** `src/DataGuard.VisualStudio/DataGuardPackage.Publishing.cs:82`; `src/DataGuard.VisualStudio/DataGuardPackage.Commands.cs:151`; `src/DataGuard.VSCode/src/extension.ts:865`; `src/DataGuard.VisualStudio/CliLocator.cs:21-33, 99-117`; `src/DataGuard.Cli/DataGuard.Cli.csproj:5,9,10`; `.github/workflows/release.yml:111,529,554`; nuget.org lookups above (404 / 0 hits).
- **Suggested fix:** Remove `dotnet tool …` guidance from both extensions until the ID is published (or reserve the `DataGuard` prefix on nuget.org today). Point to "reinstall the VSIX" and the GitHub Releases page with the SHA-256 that `release.yml:427` already produces. Longer term, verify the discovered CLI (Authenticode or the cosign bundle) before running anything that is not the bundled exe.
- **Test that would catch it:** A test that fails when any user-facing string in `src/DataGuard.VisualStudio` or `src/DataGuard.VSCode` mentions `dotnet tool install|update` while `DataGuard.Cli` is not resolvable from the configured feed (or, simpler, a guard test asserting no such string exists until a `PACKAGE_PUBLISHED` constant flips).

## Finding 2: A hostile workspace file name makes `assess` results vanish with a "CLI too old" message that funnels users into Finding 1
- **Severity:** High
- **Location:** Phase 02, section "Requirements" item 2 ("If the CLI exits 2 and stderr mentions `--ide-safe` … report 'CLI too old'"); "Security" section
- **Flaw:** Detection is a case-insensitive substring match on **every** stderr line regardless of exit code or whether progress events were seen (`ProgressStreamReader.cs:66-69`, `CliArgumentBuilder.cs:102-113`). The CLI echoes attacker-controlled workspace paths to stderr: `assess` prints `[{error.Code}] {error.Path}: {error.Message}` (`Program.cs:1775`) where `ToolError.Path` is the project file path (`ProjectInventoryReader.cs:123`). Guaranteed trigger: any `.csproj` larger than `MaxFileBytes` yields `DG1290` with that path (`:38`) — no parse failure needed; an unparsable `.csproj` (`:85`, DG1003) is a second trigger. The prior review's quoted-flag anchoring (`CliArgumentBuilder.cs:112`) does not help, because the attacker's file name contains the exact quoted token `'--ide-safe'`. Fact-check of the plan text: FAILED — the implementation does not require exit code 2 (nor 1, which is what an old System.CommandLine CLI actually returns).
- **Failure scenario:** Repo contains `Unrecognized command or argument '--ide-safe'.csproj` padded past `MaxFileBytes` (all characters are legal NTFS names). User runs Tools → DataGuard → Assess. The CLI runs correctly in ide-safe mode, produces SARIF, and also emits `[DG1290] C:\repo\Unrecognized command or argument '--ide-safe'.csproj: project file exceeds … bytes cap`. `IdeSafeUnsupported` flips; `DataGuardPackage.Commands.cs:148-154` discards the SARIF, sets status "CLI too old" and tells the user to `dotnet tool update -g DataGuard.Cli`. Every assessment of that repo is blanked, and the remediation text leads straight to the unclaimed package.
- **Evidence:** `src/DataGuard.VisualStudio/ProgressStreamReader.cs:66-69`; `src/DataGuard.VisualStudio/CliArgumentBuilder.cs:102-113`; `src/DataGuard.VisualStudio/ProgressReadModels.cs:48`; `src/DataGuard.VisualStudio/DataGuardPackage.Commands.cs:148-154`; `src/DataGuard.Cli/Program.cs:1775`; `src/DataGuard.Core/Assessment/Internal/ProjectInventoryReader.cs:85,123`; `src/DataGuard.Core/Assessment/AssessmentContracts.cs:89-99`; plan `phase-02-…md:14`; `Program.cs` has no `TreatUnmatchedTokensAsErrors` override (grep empty → default true → an old CLI exits 1 without invoking the command).
- **Suggested fix:** Treat "old CLI" as: exit code == 1 **and** no progress event of any kind was parsed **and** a stderr line *starts with* `Unrecognized command or argument '--ide-safe'`. Add a `SawAnyProgressEvent` flag to `ProgressReadResult`. Separately, have the CLI redact/relativise `error.Path` before echoing, and never let a matched detector line also be forwarded as informational output.
- **Test that would catch it:** `ProgressStreamReader` fed a `PhaseStarted` event, then `[DG1003] C:\x\Unrecognized command or argument '--ide-safe'.csproj: invalid project metadata: XmlException`, then a `Summary` event, with exit code 1 → `IdeSafeUnsupported` must be false.

## Finding 3: `--ide-safe` leaves `BaselineFilePath`, `EnableBaseline` and `SnapshotFilePath` under repository control — a hostile repo silently zeroes its own findings
- **Severity:** Medium (integrity/observability; not code execution)
- **Location:** Phase 01, section "Requirements — Functional" (enumerates what is suppressed; baseline/snapshot absent); "Success criteria"
- **Flaw:** `IdeSafePolicy.Apply` (`IdeSafePolicy.cs:24-77`) touches ground-truth mode, assembly path, connection, secret-manager, audit and telemetry — grep for `Baseline|SnapshotFile` in the file returns nothing. `ValidateContractsAsync` then applies `FilterNewViolations` whenever `EnableBaseline` (default `true`, `Configuration.cs:12`) and a repo-chosen `BaselineFilePath` exist (`Program.cs:2334-2341`), with no progress event or stderr line saying how many violations were filtered. The consent prompt (`SolutionTrustGate.cs:70-88`) never shows what the config asks for, so the "config hash re-prompts on change" defence does not help: the user sees "0 errors" and cannot tell that 40 were baselined away.
- **Failure scenario:** Upstream library repo ships `.dataguard.yml` with `BaselineFilePath: .dataguard-baseline.json` plus a baseline that fingerprints every existing violation, and a `SnapshotFilePath` snapshot matching its own SQL. A consumer opens the solution in VS to check contract hygiene before adopting it; Output pane reports "validate completed … 0 errors, 0 warnings". Nothing in VS or the CLI's ide-safe suppression line indicates that a baseline was applied.
- **Evidence:** `src/DataGuard.Cli/IdeSafePolicy.cs:24-77` (no baseline/snapshot handling — grep empty); `src/DataGuard.Cli/Program.cs:2334-2341` (`:2340` is the filter call, no emit); `src/DataGuard.Core/Models/Configuration.cs:9-12`; `src/DataGuard.VisualStudio/SolutionTrustGate.cs:70-88`; `src/DataGuard.VisualStudio/DataGuardPackage.Publishing.cs:57-73` (`ReportOutcomeAsync` has nothing to print).
- **Suggested fix:** Under `--ide-safe`, either force `EnableBaseline=false` and add it to the suppression line, or keep the baseline but emit a `BaselineApplied` progress event `{Suppressed: n, Path: …}` that the VS extension prints as a warning line and counts in the status bar. Same event for the snapshot source path (`SnapshotSource: <relative path>`).
- **Test that would catch it:** `IdeSafePolicyTests`: config with `EnableBaseline=true, BaselineFilePath="x.json"` → `Apply` result has `EnableBaseline=false` (or `Suppressed` contains "baseline"), currently fails.

## Finding 4: Attacker-controlled SQL literals hit un-timed O(n²) regexes; repo config also sets unclamped parallelism — validation burns CPU until the VS kill on every build
- **Severity:** Medium
- **Location:** Phase 01, section "Non-functional" (only "pure, unit-testable policy"; no CPU/size bound); implementation gap not covered by any phase
- **Flaw:** `ProjectCSharpSqlSource` gave every regex a 1 s timeout (`:35-65`), but the rules that run on the extracted `RawSqlDescriptor.SqlText` did not: none of the five regexes in `PhantomIdentifierRule.cs:22-40` has a `matchTimeout`, and `ProviderRuleCatalog.cs:95` registers the rule unconditionally. `SelectListRegex = \bSELECT\s+(.+?)\s+FROM\b` (Singleline) is super-linear on `"SELECT" + ' '×N + "x"`: greedy `\s+`, lazy `.+?` and the second greedy `\s+` backtrack against each other for every split of the whitespace run (at least O(N²)). The other four (`TableRefRegex`, `CteNameRegex`, `QualifiedColumnRegex`, `SimpleIdentifierRegex`) are linear but still unbounded in wall time on multi-MB input. There is no cap on literal length or on file count in the walk (`ProjectCSharpSqlSource.cs:612-660`). In addition, `.dataguard.yml` values `MaxDegreeOfParallelism`, `MaxViolationQueueSize`, `ValidationTimeoutSeconds` (`Configuration.cs:17-19`) pass through the policy untouched into `new ConcurrentValidationEngine(config.MaxDegreeOfParallelism, config.MaxViolationQueueSize)` (`Program.cs:2286`), whose ctor accepts any positive value (`ConcurrentValidationEngine.cs:21-23`).
- **Failure scenario:** Repo has a snapshot with at least one table (precondition for the rule, `PhantomIdentifierRule.cs:62-66`) and a `.cs` file containing a few 2 MB string literals of the form `"SELECT" + spaces + "x"`. With "Run Validation on Build" enabled and consent already given, every successful build spawns a CLI that pegs a core for the full `ValidationTimeoutSeconds` (300 s default) before `CliRunTimeoutHandler` kills it; `MaxDegreeOfParallelism: 4096` multiplies the thread churn. Users disable the extension.
- **Evidence:** `src/DataGuard.Core/Rules/PhantomIdentifierRule.cs:22-40, 62-66, 79, 86, 126, 151`; `src/DataGuard.Cli/ProviderRuleCatalog.cs:95`; `src/DataGuard.Core/Sources/ProjectCSharpSqlSource.cs:35-65` (contrast: timeouts present); `src/DataGuard.Core/Validation/ConcurrentValidationEngine.cs:19-24`; `src/DataGuard.Cli/Program.cs:2286`; `src/DataGuard.Cli/IdeSafePolicy.cs` (grep `MaxDegree|ValidationTimeout` empty); `src/DataGuard.VisualStudio/DataGuardPackage.Commands.cs:37-45` (build-triggered path).
- **Suggested fix:** Set `AppContext.SetData("REGEX_DEFAULT_MATCH_TIMEOUT", TimeSpan.FromSeconds(1))` at CLI startup (covers every un-timed `Regex` in Core/Adapters at once) and rewrite `SelectListRegex`/`QualifiedColumnRegex` without the lazy `.+?`/unanchored `\w*` patterns or use `RegexOptions.NonBacktracking`. Cap SQL literal length (e.g. 64 KB) in `ProjectCSharpSqlSource`. Under `--ide-safe`, clamp `MaxDegreeOfParallelism` to `ProcessorCount`, `MaxViolationQueueSize` to its default, and ignore `ValidationTimeoutSeconds`.
- **Test that would catch it:** `PhantomIdentifierRule` against `RawSqlDescriptor("SELECT " + new string(' ', 200_000))` with a one-table schema must finish under 1 s (currently multi-second and scales quadratically).

## Finding 6: CI packaging job builds and hosts an unsigned VSIX from fork pull requests
- **Severity:** Medium
- **Location:** Phase 03, section "Requirements" ("Upload the VSIX as a CI artifact (retention 7 days)"; "Runs on push/PR like other jobs")
- **Flaw:** `ci.yml` triggers on `pull_request` (`:5-7`), the `visual-studio-vsix-package` job has no same-repo guard, and it publishes the resulting `.vsix` as artifact `dataguard-visualstudio-vsix-ci` (`:183-189`). The VSIX is unsigned (Authenticode is explicitly deferred in `plan.md`). The job also runs the bundled-CLI `dotnet publish` with `RestoreLockedMode=false` on PR code (`DataGuard.VisualStudio.csproj:96`), so the package content is entirely attacker-defined for a fork PR. Fact-check: plan says `timeout-minutes: 30`, workflow has `40` (`ci.yml:134`) — FAILED, minor.
- **Failure scenario:** Fork PR with a trojaned `DataGuardPackage` (or CLI) is opened; CI passes the packaging gate and publishes the artifact under the official repository's Actions run. A maintainer or user "tries the PR build" by downloading the artifact and installing it — a per-user VSIX install with no signature check. Even without install, the official-looking download URL is useful for phishing.
- **Evidence:** `.github/workflows/ci.yml:5-7,131-134,154-158,183-189`; `src/DataGuard.VisualStudio/DataGuard.VisualStudio.csproj:89-97`; `plans/…/plan.md` "Deferred" (VSIX Authenticode signing); `plans/…/phase-03-ci-vsix-packaging-gate.md:13`.
- **Suggested fix:** Guard the upload step with `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository` (keep the packaging assertions running for forks; only skip the artifact). Name PR artifacts with the head SHA and label them "unsigned – do not install". Land Authenticode/cosign signing of the VSIX before the next release.
- **Test that would catch it:** `actionlint`/policy check asserting every `upload-artifact` step in a job reachable from `pull_request` carries a same-repo `if:` condition, or a workflow dry-run with `act -e fork-pr.json` showing the upload step is skipped.

## Finding 7: Consent is granted for a directory subtree, before the run, and never expires — a parent-folder `.sln` pre-approves every repo cloned beneath it
- **Severity:** Medium (lower confidence; bounded by ide-safe, amplifies Findings 3-4)
- **Location:** Phase 02, section "Requirements" item 1 (consent key `(solution dir, SHA-256 of .dataguard.yml)`); "Security" section
- **Flaw:** The key is `SHA256(UPPER(solutionDir) | hash(.dataguard.yml))` (`SolutionTrustGate.cs:43-68`). It does not include the solution file, the set of projects, or the CLI identity, and `RecordConsent` is written before the CLI starts (`DataGuardPackage.Commands.cs:206`), so a run that is later discarded ("CLI too old", timeout) still persists consent. Build-triggered runs (`BuildEventsHandler.cs:32-44` → `Commands.cs:37-45`) then execute with no prompt as long as the key matches — which it does for anything added under the directory later.
- **Failure scenario:** Developer keeps an "uber" `C:\src\Work.sln` for several repos and consents once. Weeks later `git clone https://…/evil C:\src\evil` (or a build step of a legitimate project vendors a hostile submodule under `C:\src`). Every subsequent build runs `validate --project C:\src` over the new code with no prompt; the consent text the user accepted named only `C:\src`. Combined with Finding 4 the new subtree can burn the full timeout on every build; combined with a user-owned snapshot it can produce Error List noise pointing into the hostile tree.
- **Evidence:** `src/DataGuard.VisualStudio/SolutionTrustGate.cs:43-68`; `src/DataGuard.VisualStudio/DataGuardPackage.Commands.cs:86-92,178-208`; `src/DataGuard.VisualStudio/BuildEventsHandler.cs:32-44`; `src/DataGuard.VisualStudio/CliArgumentBuilder.cs:81-88` (`--project` = solution directory).
- **Suggested fix:** Include the `.sln` path and a digest of the project set (from `IVsSolution` enumeration) in the key; record consent only after a run completes with a parsed Summary; add a "Forget consent for this solution" command and an expiry (e.g. 30 days) for build-triggered runs.
- **Test that would catch it:** `ComputeConsentKey(@"C:\src", "Work.sln", projects=[A,B])` must differ from `ComputeConsentKey(@"C:\src", "Work.sln", projects=[A,B,evil])` — impossible with the current 2-argument signature, which is the point.
