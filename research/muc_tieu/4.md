## Thiết kế trải nghiệm dev (dev workflow)

### Vòng đời sử dụng hàng ngày

Tôi thiết kế theo nguyên tắc đã thống nhất ở vòng redteam trước: **nhẹ khi gõ code, nặng khi CI chạy**.

```
1. Cài đặt (một lần)
   dotnet add package DataGuard.Core
   dotnet add package DataGuard.Oracle.Adapter   # optional, riêng license Oracle
   dataguard init                                 # sinh file cấu hình .dataguard.yml

2. Áp dụng vào codebase cũ (một lần, bắt buộc trước khi bật CI gate)
   dataguard baseline --connection "<oracle CI schema>"
   → sinh .dataguard-baseline.json, đóng băng mọi drift đang tồn tại, commit vào repo

3. Vòng lặp code hàng ngày (IDE, mọi editor — VS/Rider/VS Code)
   → chỉ có một cảnh báo nhẹ, syntax-level: "⚠ lời gọi SP chưa validate — chạy `dataguard check` để xác nhận"
   → không kết nối DB, không làm chậm gõ phím

4. Trước khi commit (tuỳ chọn, pre-commit hook)
   dataguard check --offline    # so với snapshot đã cache, không cần DB, chạy dưới 1 giây

5. CI trên Pull Request (gate thật)
   dataguard check --connection "<CI schema>" --format sarif --output results.sarif
   → upload SARIF, GitHub tự render annotation ngay trên dòng code trong PR
   → chỉ fail build nếu phát hiện drift MỚI (baseline cũ bị bỏ qua)

6. Khi có thay đổi schema hợp lệ (DBA đổi proc có chủ đích)
   dataguard snapshot refresh --connection "<CI schema>"
   → cập nhật lại snapshot, giống thao tác "approve" trong Jest snapshot testing — 
     một dòng diff rõ ràng trong PR review, ai duyệt PR là người xác nhận thay đổi hợp lệ
```

Bước 6 quan trọng vì nó trả lời câu hỏi ở vòng trước — "ai chịu trách nhiệm sửa": khi thay đổi là *có chủ đích*, người review PR chỉ cần thấy diff trong file snapshot và duyệt, không phải sửa code; khi thay đổi là *lỗi thật* (quên cập nhật), CI đỏ, dev tự biết phải sửa gì nhờ SARIF annotation trỏ đúng dòng.

## Thiết kế test suite cho "AI-generated code" — có taxonomy khoa học làm nền

Tôi tìm được đúng thứ cần: một nghiên cứu 2026 định lượng chính xác các loại lỗi AI tạo ra khi sinh SQL cho Oracle, dựa trên phân tích thủ công 50 câu lỗi thật:

Trong lấy mẫu thủ công 50 câu truy vấn thất bại, có 41 trường hợp là H1 (bảng/cột ma — model bịa ra tên không tồn tại), 7 trường hợp H2 (nhầm cột sang bảng khác), và 2 trường hợp H3 (nhầm dialect). Kiểu lỗi phổ biến nhất trong tập C1 là H1 — model tự bịa ra tên bảng hợp lý về mặt naming convention nhưng không tồn tại trong schema thật, ví dụ sinh ra ORDERS_SUMMARY thay vì bảng ORDERS thật — phản ánh việc model dựa vào quy ước đặt tên học được lúc pretraining thay vì schema thật được cung cấp lúc suy luận.

Đây là con số cực kỳ quan trọng cho việc định vị sản phẩm: **H1+H2 chiếm 96% lỗi (48/50)** — chính là loại lỗi module chính (entity-contract validator) bắt được trực tiếp, vì bất kỳ tên cột/bảng ma nào cũng sẽ không khớp với ground truth lấy từ `ALL_ARGUMENTS`/DESCRIBE thật. Module dialect-check (H3) chỉ chiếm 4% — vẫn đáng làm nhưng nên truyền thông đúng tỷ trọng, module chính mới là phần tạo giá trị lớn nhất.

Nghiên cứu khác củng cố thêm ví dụ cụ thể cho H3 mà tôi dùng làm test case thật: LLM có xu hướng hallucination hoặc chuyển thẳng hàm từ dialect phổ biến khác (như MySQL) sang database đích — ví dụ khi cần gộp chuỗi, các baseline generate nhầm hàm GROUP_CONCAT của MySQL cho Oracle (đúng ra phải là `LISTAGG`).

### Bộ test corpus (golden corpus) theo taxonomy

```
tests/golden-corpus/
├── H1_phantom_identifier/
│   ├── case_01_invented_table.sql      -- SELECT * FROM ORDERS_SUMMARY (không tồn tại)
│   ├── case_02_invented_column.cs      -- entity có property AI bịa, DB không có cột đó
│   └── expected_diagnostics.json       -- danh sách lỗi tool PHẢI báo ra
├── H2_column_table_mismatch/
│   └── case_01_wrong_table_column.sql  -- cột thật nhưng gán nhầm bảng trong join
├── H3_dialect_confusion/
│   ├── case_01_mysql_group_concat.sql  -- GROUP_CONCAT thay vì LISTAGG
│   ├── case_02_limit_vs_fetch.sql      -- LIMIT thay vì FETCH FIRST n ROWS ONLY
│   └── case_03_pivot_bracket.sql       -- ngoặc vuông kiểu SQL Server trong PIVOT Oracle
└── length_mismatch/
    └── case_01_varchar2_overflow.cs    -- string C# dài hơn cột VARCHAR2(n)
```

Mỗi case là một **regression test cố định** — assert rằng `dataguard check` trên input đó phải sinh đúng diagnostic code kỳ vọng, không hơn không kém (tránh cả false negative lẫn false positive).

### Nguồn thu thập case thật — vòng lặp về đúng ràng buộc ban đầu của bạn

Đây là chỗ tôi khép lại đúng ý tưởng gốc của bạn (dùng free tier của nhiều AI provider): thay vì tôi tự bịa test case, **dùng chính nhiều AI model free tier để tạo ra hallucination thật**, biến điểm yếu của AI thành nguồn dữ liệu test cho chính công cụ chống lại nó:

1. Dựng một schema Oracle mẫu (Testcontainers.Oracle + gvenzl/oracle-xe, đã xác nhận khả thi ở vòng trước) mô phỏng bảng enterprise thật (naming convention viết hoa, có FK, có package chứa procedure overload).
2. Prompt nhiều model qua free tier khác nhau (ví dụ các model miễn phí qua OpenRouter, Gemini free tier, DeepSeek, Qwen) với các task DAO-layer thực tế: *"viết Dapper query lấy top 10 khách hàng theo doanh thu từ schema này"*.
3. Chạy từng SQL/C# sinh ra thật trên Oracle XE — case nào lỗi (ORA-00904, ORA-00907...) hoặc kết quả sai được đưa vào golden corpus, gắn nhãn đúng H1/H2/H3/H4 theo taxonomy trên.
4. Corpus này tự lớn dần theo thời gian mỗi khi có model mới ra mắt — trở thành tài sản độc quyền của riêng dự án, khó sao chép, và là bằng chứng thuyết phục nhất cho hồ sơ Anthropic: *"đây là 200 case hallucination thật từ N model khác nhau, tool bắt được X%"* — con số thực nghiệm mạnh hơn nhiều so với mô tả lý thuyết.

### Ma trận test 3 tầng

| Loại test | Cần DB? | Tốc độ | Mục đích |
|---|---|---|---|
| Unit test | Không (mock ground truth) | ms | Logic diff engine, normalize naming |
| Integration test | Có (Testcontainers Oracle XE) | giây–phút | ALL_ARGUMENTS/DESCRIBE thật hoạt động đúng |
| Golden corpus regression | Có, chạy định kỳ | phút | Đo % hallucination thật bắt được, theo dõi qua thời gian |
