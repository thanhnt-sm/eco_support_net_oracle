## Module chính (MVP) — **Entity ↔ SP/Raw SQL contract validator**

### Vì sao đây là gap chưa ai build

Microsoft đã theo dõi issue `dotnet/efcore#245` ("Map inserts, updates, and deletes to stored procedures") từ tháng 5/2014, vẫn mở và từng được đưa vào plan cho EF Core 7.0 nhưng không hoàn thành 【turn1search0】【turn1search1】. Cùng lúc đó, các nhánh về `FromSql`/`FromSqlRaw` liên tục lỗi runtime mà EF Core không kiểm tra ở design-time:

- `#10398` — `FromSql` không nhận parameter được đặt tên đúng khi gọi SP 【turn1search1】
- `#11344` — `FromSql` bắt buộc `SqlParameter` nếu tên biến dài, lỗi "Must declare the scalar variable" 【turn1search1】
- `#28192` — `DbSet.FromSqlRaw` ném `The required column 'Id' was not present in the results of a 'FromSql' operation` ngay khi SP trả result set thiếu cột 【turn1search3】
- `#11624` — `FromSql` bắt buộc register type trước, nếu không crash runtime 【turn1search0】
- `#37096` — đến .NET 10 preview vẫn còn conflict tên biến `@p0` khi compose LINQ trên `FromSqlRaw` 【turn1search3】

Trên ecosystem bên ngoài, không công cụ nào close gap này:

- **EFCorePowerTools** scaffold SP nhưng chỉ generate code gọi, không validate contract; hơn nữa phụ thuộc `SET FMTONLY` nên không support hết mọi SP 【turn1search8】【turn1search6】
- **EFCore.Testing / EntityFrameworkCore.Testing** chỉ mock `DbContext` để unit test, không kiểm tra contract thực 【turn0search0】
- **EF Core In-Memory provider** chính thức không support stored procedure, nên test integration phải dùng SQLite/SQL Server thật 【turn1search3】
- **FluentAssertions.EFCore** không có matcher cho SP contract

=> Khoảng trống là "design-time static contract check" giữa entity model và SQL contract, chưa có OSS nào làm.

### Các bước triển khai MVP

**1. Extract entity metadata từ EF Core `IModel`**

Đọc `IModel` runtime qua `DbContextOptions` hoặc qua design-time service `IDesignTimeServices` 【turn0search10】. Duyệt `IEntityType` → `IProperty`, lấy:

- `property.GetColumnType()` (provider-specific, ví dụ `NVARCHAR2(50)`)
- `property.IsNullable()`
- `property.GetMaxLength()`
- `property.GetProviderClrType()` vs `property.ClrType`

Một cách ổn định hơn là parse file `<Context>ModelSnapshot.cs` được EF Core tự sinh khi add migration 【turn1search19】 — tránh phụ thuộc runtime state.

**2. Extract SP parameter & result shape**

Với Oracle, query `ALL_ARGUMENTS` join `ALL_PROCEDURES` 【turn1search12】【turn1search13】:

```sql
SELECT args.argument_name, args.in_out, args.data_type,
       args.data_length, args.data_precision, args.data_scale, args.position
  FROM sys.all_procedures proc
  LEFT JOIN sys.all_arguments args ON proc.object_id = args.object_id
 WHERE proc.owner = :owner AND proc.object_name = :procName
 ORDER BY args.position;
```

Với SQL Server, dùng `sys.parameters` + `sp_describe_first_result_set` (tương đương `SET FMTONLY` mà EFCorePowerTools dùng 【turn1search8】).

Với raw SQL (không phải SP), dùng **Microsoft.SqlServer.TransactSql.ScriptDom** (T-SQL) hoặc parser riêng cho Oracle PL/SQL để tách danh sách tham số và danh sách cột `SELECT`.

**3. So khớp contract**

Tập hợp các rule ban đầu:

- `ParameterTypeMatchRule` — CLR type ↔ Oracle/SQL Server type mapping (dùng bảng `Oracle.ManagedDataAccess` type mapping 【turn1search15】)
- `ParameterCountRule` — SP có parameter mặc định thì cho phép subset, không thì match exact
- `ParameterDirectionRule` — `IN/OUT/INOUT` ↔ tham số `out`/`ref` trong C#
- `ColumnShapeMatchRule` — result set phải có đủ các property mapped của entity (EF Core bắt buộc "SQL query must return all the properties of the entity type" 【turn0search15】)
- `NullableMismatchRule` — cột `NOT NULL` ↔ property non-nullable
- `NamingConventionRule` — column ↔ property name theo naming convention của provider (ví dụ snake_case ↔ PascalCase)

**4. Emit diagnostic**

Xuất theo 3 kênh:

- **Roslyn analyzer** chặn `FromSqlRaw`/`FromSqlInterpolated`/`ExecuteSqlRaw` — cắm `SyntaxNodeAnalyzer` vào `InvocationExpression`
- **CLI runner** xuất SARIF 2.1 để tích hợp GitHub Code Scanning / Azure DevOps
- **Markdown/HTML report** để review nhanh

Ví dụ diagnostic mẫu:

```
EFV1001  Parameter '@CustomerId' on SP 'dbo.GetOrders' is VARCHAR(20)
         but EF entity 'Order.CustomerId' has MaxLength=50 — runtime truncation risk.

EFV1002  SP 'pkg_orders.get_by_id' result set missing required column
         'ORDER_DATE' that entity 'Order' maps via FromSql.

EFV1003  Parameter '@Total' declared OUT in SP but C# call site passes
         it as input-only (no 'out'/'ref').
```

## Module mở rộng — **Oracle dialect-check + length-mismatch check**

### 2a. Oracle dialect-check

Mục tiêu: cảnh báo khi raw SQL hoặc SP dùng cú pháp không portable hoặc không khớp provider option trong `DbContextOptions`.

Rule cụ thể:

| Rule | Mô tả | Nguồn bằng chứng |
|---|---|---|
| `OracleSyntaxInNonOracleContext` | `DECODE`, `NVL`, `(+)` outer join, `DUAL`, `seq.NEXTVAL`, `ROWNUM`, `CONNECT BY` xuất hiện nhưng `UseSql*` không phải Oracle | Cú pháp Oracle-specific 【turn1search19】 |
| `NonOracleFunctionInOracleContext` | `ISNULL`, `TOP n`, `GETDATE()` (SQL Server style) dùng trong context Oracle | — |
| `ProviderOptionMismatch` | `DbContextOptions` không đăng ký `UseOracle` nhưng metadata reader Oracle trả kết quả | `EFCoreProvider` config 【turn1search12】 |
| `SqlServerSyntaxLeak` | `EXEC dbo.Sp` thay vì `BEGIN ... END;` block của Oracle | EF doc khuyến nghị `EXECUTE` cho SQL Server 【turn0search0】 |
| `RawSqlUnmappedTypeUsage` | Dùng `SqlQueryRaw<T>` cho type chưa được provider map (Oracle EF Core 8 mới thêm raw SQL cho unmapped type) 【turn0search10】 | Oracle EF Core 8 release notes |

Cài đặt: dùng ScriptDom (T-SQL) hoặc một parser PL/SQL riêng (PlSqlParser open-source hoặc tự viết ANTLR grammar) để detect token, rồi áp rule table.

### 2b. Length-mismatch check (giải quyết "data too long")

Đây là phần giải quyết trực tiếp ORA-12899 — lỗi runtime "value too large for column" 【turn0search10】【turn0search11】.

**Vấn đề gốc rễ** (đã được Microsoft xác nhận qua `dotnet/efcore#33218`):

> Trong Oracle provider, tuỳ thuộc vào giá trị `size`, một CLR `string` maps hoặc `VARCHAR2`/`NVARCHAR2` hoặc `CLOB`/`NCLOB`. Khi `size=null` (thường khi SqlConstantExpression không có TypeMapping), Oracle provider fallback về `NVARCHAR2(2000)` 【turn1search18】.

Ngoài ra có 3 nguồn mismatch:

1. **Char vs Byte semantics** — `VARCHAR2(50)` có thể là 50 ký tự hoặc 50 byte tuỳ `NLS_LENGTH_SEMANTICS` của session 【turn0search10】. Nếu entity set `HasMaxLength(50)` nhưng DB column là `VARCHAR2(50 BYTE)` và app lưu Unicode, dễ tràn.
2. **EfCore inference** — size inference dựa trên binary expression có thể nhầm `null` size thành NVARCHAR2(2000) 【turn1search18】.
3. **Entity length vs column length** — entity set `HasMaxLength(500)` nhưng column trong `ALL_TAB_COLUMNS.CHAR_LENGTH` chỉ 200.

**Implementation:**

```csharp
// EfCoreInferenceSimulator.cs — giả lập thuật toán infer type của Oracle provider
// để dự đoán xem EF sẽ gửi column type nào
public OracleColumnType Predict(IProperty property, string? sqlFragment)
{
    var maxLen = property.GetMaxLength();
    if (maxLen is null && property.IsUnicode() == true)
        return OracleColumnType.NVarchar2(2000); // mirror #33218 behavior
    ...
}

// LengthSemanticsResolver.cs — đọc NLS_LENGTH_SEMANTICS của session
public async Task<LengthSemantics> ResolveAsync(DbConnection conn)
{
    await conn.OpenAsync();
    using var cmd = conn.CreateCommand();
    cmd.CommandText = @"SELECT value FROM nls_session_parameters
                        WHERE parameter = 'NLS_LENGTH_SEMANTICS'";
    var v = (string)(await cmd.ExecuteScalarAsync())!;
    return v == "CHAR" ? LengthSemantics.Char : LengthSemantics.Byte;
}

// LengthMismatchDetector.cs — so sánh entity MaxLength với ALL_TAB_COLUMNS
public IEnumerable<ContractViolation> Detect(
    EntityDescriptor entity,
    OracleColumnDescriptor column,
    LengthSemantics sessionSemantics)
{
    // 1. Mismatch thuần length
    if (entity.MaxLength > column.CharLength)
        yield return new LengthExceedsColumnViolation(...);

    // 2. Mismatch semantics
    if (sessionSemantics == LengthSemantics.Byte
        && entity.MaxLength.HasValue
        && column.CharLength < entity.MaxLength * MaxBytesPerChar(entity.IsUnicode))
        yield return new ByteLengthOverflowRiskViolation(...);

    // 3. CLOB/VARCHAR2 switching risk (mirror #33218)
    if (entity.MaxLength is null && column.DataType != "CLOB")
        yield return new InferredSizeFallbackViolation(
            "EF sẽ infer NVARCHAR2(2000), có thể gây ORA-12899 khi giá trị > 2000 bytes.");
}
```

**Query metadata Oracle:**

```sql
-- Lấy column length chính xác theo semantics
SELECT column_name, data_type, data_length, char_length,
       char_used  -- 'B' = BYTE, 'C' = CHAR
  FROM all_tab_columns
 WHERE owner = :owner AND table_name = :tableName;
```

`char_used` cho biết column nào dùng CHAR semantics, cột nào dùng BYTE — là chìa khóa để chặn ORA-12899 【turn0search10】【turn0search12】.

## Lưu ý về giới hạn nghiên cứu

- Module chỉ validate contract **static** — không thực thi SP, nên SP có SQL động phức tạp (dynamic SQL trong `EXECUTE IMMEDIATE`) sẽ không parse hết được, cần đánh dấu "manual review required".
- `IModel` snapshot có thể lệch code hiện tại nếu dev quên `dotnet ef migrations add`; cần dùng `IDesignTimeServices` để rebuild model từ source 【turn0search10】.
- Oracle provider có behavior đặc thù khi infer type (xem `#33218`) — cần pin version `Oracle.ManagedDataAccess.Core` tương ứng với EF Core version đang dùng, vì thuật toán infer có thể thay đổi giữa release 【turn1search18】.
- `EFCorePowerTools` dùng `SET FMTONLY` để sniff result shape, cách này không hoạt động với mọi SP 【turn1search8】 — nên ưu tiên `ALL_ARGUMENTS` cho Oracle và `sp_describe_first_result_set` cho SQL Server.
